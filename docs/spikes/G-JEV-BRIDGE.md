**Редакция секретов (`redact`).** Вырезается два класса:

- значения-секреты: `whsec_…`, `sk_live_…`, `sk_test_…`, `pk_live_…`, `Bearer …`, `postgres://`, `postgresql://`, `mysql://`, `redis://`, `-----BEGIN` — значение заменяется на `<redacted>`.

**Пределы (превышение → `skip`, усечения нет):**

| Предел | Значение | Почему |
| --- | --- | --- |
| `STATE_MAX_BYTES` | 24 576 байт (24 KiB) сериализованного state | у модели 64k контекста, из них 32k на state + самый длинный вопрос; 24 KiB ≈ 6k токенов — с запасом |
| `STATE_MAX_KEYS` | 40 полей | защита от «простыни» вместо состояния |
| `STATE_VALUE_MAX_CHARS` | 4 000 символов на значение | одно поле не должно съедать бюджет |

Молча изменённый вход — это подмена входа, а не экономия байтов: не влезло — `skip`, решение остаётся за ROMA (`contract.oversized_field`).

## 2. Spike-набор вопросов (три, одним вызовом)

Все три уходят **одним** вызовом `system_one` — они независимы и не видят ответов друг друга. Формулировки зафиксированы в `contract.questions`; идентификаторы вопросов нужны только коду.

| id | Примитив | Формулировка (суть) | Ответ |
| --- | --- | --- | --- |
| `gate` | `noul` | «Данных достаточно, чтобы безопасно продолжить исполнение без ручного разбора: очередь и регион известны, доступность воркеров не противоречива, повторов меньше трёх» | вероятность «да» |
| `next` | `choice` | «Что делать с задачей прямо сейчас, если решение принимает оператор: запустить / задать уточняющий вопрос / отказаться» | `run` \| `ask` \| `abort` + распределение + confidence |
| `risk` | `score` | «Оцени риск исполнения по фиксированной шкале 1–5: 1 — рутина, 5 — отказ или потери» | уровень 1–5 + распределение + confidence |

`noul` намеренно **без** `criteria`-порога внутри модели: порог — политика кода (§3). У `choice` максимум 255 вариантов, у `score` — до 10 уровней; здесь 3 и 5 соответственно.

## 3. Пороги execute / confirm / abort (политика кода, не модели)

`contract.THRESHOLDS`:

| Порог | Значение | Смысл |
| --- | --- | --- |
| `gate_execute` | 0.70 | выше — исполнение допустимо |
| `gate_confirm` | 0.45 | 0.45–0.70 — нужно подтверждение |
| `choice_execute` | 0.60 | выбранное `run` должно иметь такую вероятность |
| `choice_confirm` | 0.45 | ниже — сигнала на подтверждение нет |
| `risk_confirm` | 3.5 | выше — исполнение запрещено, только подтверждение |
| `confidence_floor` | 0.50 | ниже уверенности — `skip`, а не догадка |

Порядок правил (`adapter.decide`):

1. домен запрещён → `skip`;
2. ответов нет / тип не тот / `choice` вне `{run,ask,abort}` / нет `confidence` / `risk` вне шкалы → `skip`;
3. `confidence < 0.50` → `skip` (причина `low_confidence`);
4. `risk > 3.5` → **`confirm`** (никогда `execute`);
5. `gate ≥ 0.70` **и** `next = run` **и** `P(run) ≥ 0.60` → **`execute`**;
6. `gate ≥ 0.45` **или** `next = ask` **или** `P(run) ≥ 0.45` → **`confirm`**;
7. иначе → **`abort`**.

`confidence` берётся из ответа `next` (у `noul` уверенности нет по формату примитива — поэтому решение никогда не строится на `gate` без `next`).

### Шкала `risk` и нецелые значения

`risk` — дискретный `score` по фиксированной шкале `RISK_LEVELS = (1, 2, 3, 4, 5)`; риск растёт с уровнем. Провайдер может вернуть нецелое значение, поэтому отображение в уровень зафиксировано явно (`adapter._risk_value`), и порядок шагов — часть контракта:

1. `bool` и `None` отсекаются **до** приведения. `True` — подкласс `int`; без этого гейта он стал бы уровнем `1` и разрешил `execute`.
2. Строка обрезается (`strip`). Пустая строка → `skip`. `float()` не удался → `skip`.
3. `math.isfinite` отсекает `NaN` и `±inf`, включая строки `"nan"`, `"inf"`, `"Infinity"`.
4. Диапазонный гейт по **сырому** значению: вне `[1, 5]` → `skip`. Округление раньше гейта запрещено: `0.6` иначе стало бы `1` и ушло в `execute`.
5. Прошедшее значение округляется `math.floor(x + 0.5)` (half-up). На этой положительной шкале ровно `.5` идёт к более рискованному уровню. `round()` не используется: у него half-even (`2.5 → 2`, `4.5 → 4`).

С действием сравнивается уже целый уровень и порог `risk_confirm = 3.5` (`level > 3.5`, то есть уровень ≥ 4):

| Вход | Уровень | Почему |
| --- | --- | --- |
| ровно `1…5` (в т.ч. `"3"`, `"3.0"`) | как есть | прямое попадание в шкалу |
| нецелое внутри `[1, 5]` | `floor(x + 0.5)` (ровно `.5` — вверх, к более рискованному уровню) | округление вверх не делает решение мягче: `3.5 → 4` (confirm), `2.5 → 3`, `4.5 → 5`, `3.4 → 3` |
| вне `[1, 5]` (`0.6`, `0`, `-1`, `5.5`, `6`) | `None` → `skip` | «`risk` вне шкалы → `skip`» (шаг 2 выше) |
| `NaN`, `±inf` (в т.ч. строки `"nan"`, `"inf"`) | `None` → `skip` | не число на шкале; наружу не исключение, а `skip` |
| `True` / `False` | `None` → `skip` | `bool` — не число (в Python `bool` — подкласс `int`) |
| `None`, `"abc"`, `""`, `"  "` | `None` → `skip` | в число не разбирается |

**Fail-closed инвариант:** ни нецелое значение, ни его округление не переводят решение в более разрешительную ветку, чем допускают соседние уровни и непрерывное значение. Python `round()` (banker's rounding) не используется: семантика ровно `.5` задана явно и закреплена тестами (`2.5 → 3`, а не `2`).

**Против `round()` действие на этой шкале не меняется** (`3.5` и там, и там → `4` → `confirm`); меняется сохраняемый уровень: `2.5` было `2`, стало `3` (оба `execute`); `4.5` было `4`, стало `5` (оба `confirm`); `1.5` остаётся `2`. Потребитель, который читает уровень, а не только `action`, видит смену на `2.5` и `4.5`.

**Против сравнения сырого `value > 3.5`** действие меняется только в точке ровно `3.5`: сырое сравнение не проходит, уровень `4` проходит → `confirm`. Интервал `[3.5, 4)` меняет действие относительно `floor()` без half-up, не только точка `3.5`.

## 4. Лимиты

`contract.LIMITS`:

| Лимит | Значение |
| --- | --- |
| `timeout_s` | 8.0 на один вызов |
| `retries` | 1, и только на 429/529 (таймаут не повторяем — иначе бюджет latency тратится дважды) |
| `retry_backoff_s` | 0.5 → ×2 на повторе |
| `max_calls_per_run` | 1 сетевой вызов на запуск адаптера (три вопроса — один вызов) |
| `latency_budget_s` | 12.0 — объявленный ориентир; **в коде как гейт не проверяется**. Фактический худший случай одного запуска = `timeout × 2 + retry_backoff_s` = 16.5 s (первый вызов 429 → один повтор → таймаут), то есть ориентир ниже расчётного потолка |

## 5. Fallback: адаптер возвращает `skip`, не исключение

| Ситуация | Решение | Причина (`reason`) | Сеть |
| --- | --- | --- | --- |
| `JEV_ENABLED` выключен или пуст | `skip` | `disabled` | нет |
| `TYPESAFE_API_KEY` пуст | `skip` | `disabled` | нет |
| 429/529 после единственного повтора | `skip` | `rate_limited` | да |
| таймаут | `skip` | `timeout` | да |
| ответ не JSON / чужой HTTP-статус | `skip` | `bad_answer` | да |
| ответ разобран, но форма битая | `skip` | `bad_answer` | да |
| `confidence < 0.50` | `skip` | `low_confidence` | да |
| state не объект / полей > 40 | `skip` | `bad_state` | нет |
| state > 24 KiB или значение > 4 000 символов | `skip` | `state_too_large` | нет |
| превышен лимит вызовов | `skip` | `call_limit` | да |
| прочий сбой транспорта | `skip` | `transport_error` | да |
| сбой вне транспорта: своя логика клиента, SDK упал на конструкторе | `skip` | `internal_error` | да |

`skip` — это «адаптер не имеет мнения», а не «нет». Никакое исключение наружу не выходит, никакое решение ROMA не подменяется: `execute` и `abort` никогда не выводятся из неполных данных.

`detail` в `evidence` проходит через `client.mask(text, key)`: из текста вырезается и литерал ключа (сырой и URL-encoded), и шаблоны (`whsec_…`, `sk_live_…`, `Bearer …`, DSN), затем длина режется до 300 символов.

## 6. Запрещено адаптеру

`contract.FORBIDDEN_DOMAINS = ("payment", "billing", "deploy", "delete", "quota")`.

Запрос вопроса или state с доменом из списка (в том числе через поле `act`) → `skip` с причиной `forbidden_domain`, **без** обращения к сети. Адаптер не решает: оплату, списание, деплой, удаление, квоты. Он также не строит собственный gateway и не проксирует чужие ключи.

## 7. Модель, ключ, endpoint

- Модель: `jev-1.13.0` (`contract.DEFAULT_MODEL`). `jev-latest` — **только** ручной smoke, с предупреждением в stderr (`--model jev-latest`); в регулярном пути он не используется.
- Endpoint: ровно `POST https://api.typesafe.ai/v1/systemone`. Ключ — только `TYPESAFE_API_KEY` из env процесса: фермерские ключи, временная почта, сторонние прокси и проброс клиентского ключа запрещены. Ключ не логируется и не коммитится; в текстах ошибок маскируется (`client.mask`).
- Официальный SDK (`typesafe_sdk.TypeSafeClient.system_one`) предпочтителен, если установлен; иначе тот же endpoint через stdlib. SDK **не** обязателен для установки и запуска ROMA и в её зависимости не входит (`adapters/jev/requirements-jev.txt`, ставится только по желанию оператора).

## 8. Внешняя точка входа

```bash
# вердикт в stdout
python -m adapters.jev.run --state-file state.json

# вердикт в файл; --model jev-latest — только ручной smoke
python -m adapters.jev.run --state-file state.json --out decision.json

# явный домен операции (иначе берётся поле act)
python -m adapters.jev.run --state-file state.json --domain compute
```

Коды выхода: `0` — только `execute` / `confirm` / `abort`; `4` — `skip` (адаптер не имеет мнения; нулевой код намеренно не отдаётся, иначе внешний вызывающий принял бы «нет мнения» за разрешение); `2` — ошибка использования; `3` — state не прочитан; `5` — вердикт получен, но `--out` не записан (ошибка вывода: целевой файл не тронут, частичный JSON не остаётся, вердикт не переклассифицируется в `skip`, провайдер повторно не вызывается) — это ошибка вывода, не `skip` и не ошибка использования. Формат вердикта:

```json
{
  "decision": "execute | confirm | abort | skip",
  "reason": "gate_and_choice | insufficient_signal | gate_below_floor | risk_above_execute | disabled | ...",
  "evidence": {"gate_noul": 0.91, "next_choice": "run", "next_probability": 0.88, "risk_score": 2.0, "confidence": 0.9},
  "model": "jev-1.13.0",
  "latency_ms": 412.5
}
```

`evidence` содержит только вероятности и счётчики — ни ключей, ни тел запросов.

## 9. Проверки адаптера (вне прогона ядра)

```bash
.venv/bin/python -m pytest adapters/jev/checks/jev_checks.py -q
```

123 проверки, HTTP-мок без сети и без живого ключа: флаг выключен, нет ключа, таймаут, 429 с исчерпанием повтора, официальный endpoint и ключ из env, низкая уверенность, нет `choice`, не-JSON, валидный `choice` одним вызовом, `gate` ниже порога, `ask` → confirm, высокий риск не исполняется, запрещённый домен (вопросом и через `act`), превышение значения без усечения, превышение байтового лимита, неверный тип state, секреты не доходят до транспорта, ключ не попадает в лог, `state_fits` считается по сериализованным байтам, путь SDK предпочитается при наличии, чужое исключение из транспорта и падение SDK на конструкторе гасятся в `skip` без исключения наружу, ключ вырезается из `detail` даже без слова `Bearer`, вложенные секреты (dict/list/tuple) не доходят до транспорта, коды выхода CLI: `0` — вердикт записан (execute/confirm/abort), `2` — ошибка использования (argparse, `SystemExit(2)`; константа `EXIT_USAGE`), `3` — state не прочитан, `4` — skip при успешной записи, `5` — ошибка вывода `--out` (`OSError` на записи или `os.replace`; не skip и не ошибка использования); матрица `risk` (нецелые, ровно `.5`, около бизнес-порога, границы шкалы, `None`, строки, `bool`, `NaN`, `±inf`, вне диапазона) на уровне `_risk_value` и на уровне итогового `action`; `NaN`/`inf` не выходят наружу исключением; сбой `--out` (реальный `OSError`, `PermissionError`, `os.replace`) даёт код `5` без переклассификации в `skip`, без повторного вызова провайдера, без частичного JSON и без временного файла, с маскированием ключа в диагностике; успешная запись сохраняет структуру вердикта и прежние коды.

Файл назван `jev_checks.py` (не `test_*.py`) осознанно: канон прогона ядра — repo-wide `collected == 486` (`.ci/run-completeness.json`), и добавление собираемого теста сдвинуло бы канон. Дискавери по `adapters/` даёт `no tests collected`; проверки запускаются явным путём. Существующие тесты ROMA не изменены и не помечены skip.

## 10. Что НЕ сделано и что не подтверждено

**Не сделано (осознанно, по границам эпохи):**

- ядро не менялось: `git diff` по планировщику, шедулеру, decision-gate, биллингу, Stripe, CloudPayments и раннерам пуст; новых импортов Jev в ядре нет; `pyproject.toml` не тронут;
- врезки в горячий путь нет. Слота решения в ядре нет (`scheduler.slurm_plugin` — слот исполнения, а не решения), поэтому подключение к ядру потребовало бы правки горячего пути — это следующая эпоха, не эта;
- миграции, меняющей ядро следующим коммитом, нет.

**Не подтверждено (нужен живой прогон владельца):**

- **живой вызов провайдера не выполнялся**: ни одного POST на `api.typesafe.ai`, ключ не подставлялся; проверки идут на моке транспорта;
- форма ответа HTTP (`answers` / `probabilities` / `confidence`) взята из официальной документации, а не из живого ответа;
- путь официального SDK проверен только на подставленном модуле-заглушке, не против сервиса;
- пороги 0.70 / 0.45 / 0.60 / 3.5 / 0.50 — стартовая политика, не калибровка на данных ROMA;
- личный кабинет провайдера не читался (нет доступа из этой машины).

Источники контракта: [HTTP API](https://docs.typesafe.ai/api.md), [примитивы](https://docs.typesafe.ai/primitives.md), [модели](https://docs.typesafe.ai/models.md), [уверенность](https://docs.typesafe.ai/confidence.md).
